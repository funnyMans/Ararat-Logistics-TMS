# TMS implementation-readiness matrix

This matrix translates accepted TMS decisions and the open-decision register
into capability-specific implementation gates. It is a readiness index, not
a new business specification, service design, implementation plan, or release
approval.

The [system blueprint](TMS_SYSTEM_BLUEPRINT.md) remains the authority for the
approved platform-foundation phase. The [technical workflow](TECHNICAL_WORKFLOW.md)
and [service contracts](../contracts.md) own shared technical invariants and
cross-service semantics. The [API index](../api/README.md) identifies
machine-readable contract coverage. The [open-decision register](OPEN_QUESTIONS.md)
remains authoritative for unresolved requirements and their rationale.

## How to use this matrix

Readiness is assessed per capability, operation, and workflow, not once for
the entire TMS or for a service name. A capability is ready for its next
implementation increment only when all applicable gates in its row are
closed, documented, and testable. An unrelated open decision does not block
that increment.

| Status                                 | Meaning                                                                                                                                                                         |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Approved to start**                  | The bounded increment has an accepted scope and documented acceptance criteria.                                                                                                 |
| **Accepted locally**                   | The F0–F5 platform foundation has passed its documented local acceptance evidence; production qualification remains separate.                                                   |
| **Conditional**                        | The baseline is substantially defined, but listed capability-specific gates must be completed before the dependent operation or workflow is implemented.                        |
| **Blocked on owner decision/evidence** | A business, authority, source, or policy choice is unresolved; implementation must not choose one by convenience.                                                               |
| **Production qualification**           | Local implementation may proceed when its capability gates are met, but production enablement requires additional operational, provider, legal, privacy, or retention evidence. |

At present, only selected Load and Execution HTTP operations are represented.
AsyncAPI files represent selected Load, Execution, Capacity Commitment, and
Dispatch Planning messages. All current specifications are explicitly
partial.

Before implementing an operation or durable message flow, its owner and
consumers must have:

1. The exact request/message, success and business-rejection outcome, and
   idempotency/replay behavior represented in the owner contract.
2. The operation-level authorization and actor/resource boundary.
3. The required authoritative inputs, their freshness/validity, and the
   fail-closed behavior when an input is missing or stale.
4. The durable state and recovery boundary for duplicate delivery, timeout,
   partial completion, owner outage, and reconciliation.
5. Nominal and deterministic failure-path acceptance assertions against
   persisted owner state, including audit evidence and an actionable
   terminal or pending-recovery outcome.

The overall acceptance principles are selected in D-505; foundation evidence
is selected in D-504; durable idempotency, owner-correct recovery, and
capability-scoped fault testing are selected in D-510. These shared rules do
not replace the exact scenarios and measurable outcomes required for each
capability. Detailed customer-facing release scope and selection of the first
business vertical slice remain open; neither is necessary to start the
approved platform foundation.

| Workflow                   | Minimum implementation evidence derived from settled rules                                                                                                                                                                                                                                                                            |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Booking                    | Accepted/rejected outcomes are durable and replay-safe; invalid row content preserves agreed follow-up/rejection behavior; unavailable current Customer status fails closed with the specified retryable outcome.                                                                                                                     |
| Amendment and cancellation | Revision immutability and conditional updates hold under races; duplicate commands do not duplicate transitions; owner confirmations and reconciliation determine completion; active-Assignment revalidation expiry and release recovery have executable coverage before enabling that handoff.                                       |
| Planning and reservation   | Missing/stale source facts cannot pass hard gates; matching uses the approved deterministic rules; reservation contention is atomic; retried delivery is side-effect safe; activation refusal produces the agreed release/replan or audited recovery path.                                                                            |
| Execution and evidence     | Assignment handoff is idempotent; milestones and corrections are append-only; closeout records actual delivered/undelivered quantities and locations; issue handoff does not block terminal closeout; upload expiry/finalization retries, scan rejection, and cancellation-before-start preserve the selected states and audit trail. |
| Notification               | Delivery retries/requeue preserve durable attempts; receipt acknowledgement does not resolve business work; urgent required notices cannot be suppressed by user preference.                                                                                                                                                          |
| Operations View            | Duplicate, missing, stale, and corrected owner facts are visible/reconciled; projections never authorize or mutate owner records; corrections trigger required recalculation.                                                                                                                                                         |

Capability-specific failure injection and measurable acceptance must be
recorded with the selected implementation increment. This table summarizes
already-agreed invariants; it does not define unapproved business outcomes.

## Documentation structure after platform foundation

The current business and cross-service documents remain the shared
foundation. Do not create one copy of their rules per service. After platform
foundation is verified, add service-specific documentation for the business
capabilities selected for implementation. Each service dossier should link
to the shared source documents and explain only its own workflow, owner
records, operations and messages, authorization matrix, failure/recovery
runbooks, and acceptance evidence. Keep machine-readable API contracts in
`docs/api/`; keep business-wide policy in its existing business documents.
The per-service directory layout and first business slice are deliberately
deferred until that implementation sequence is selected.
